# AnthroForge standalone application requirements

Updated: 2026-10-15. Scope: preferences derived from this thread's editing responsiveness, slow computation, viewport clutter, transparency, and hover investigations.

The strongest reason for a specialized application is ownership of the interaction loop, anatomical data, and viewport presentation. A user should be able to edit, navigate, understand pending work, and choose the intended anatomical entity while expensive calculations continue. Moving the same synchronous orchestration into another window would preserve many of the delays we measured.

The October 12 production-file audit recorded a 310.91 ms shortcut setter with zero fiber solves or iterations. Experimental batching reduced two approximately 300 ms setters to approximately 194 ms and 168 ms, with the captured geometry hashes matching. These are observations about the audited addon and one fixture, not a measured limit of Blender or a prediction for a standalone application. See [the UX analysis and evidence](interaction_ux.md).

The tables distinguish three sources of motivation: **Host** means an integration boundary in Blender's addon APIs; **Addon** means behavior in AnthroForge that can also be improved while it remains an addon; **UX** means a specialized product choice whose benefit needs task testing. A standalone implementation must earn the proposed improvements on production files.

## Responsive editing and computation

| Requirement | What I would prefer in the application | Connection to the work in this thread |
| --- | --- | --- |
| R01 Native anatomical document | Own SCP, fiber, muscle, attachment, and relationship data in a typed document with stable IDs. Give C++ workers immutable or explicitly owned input snapshots and versioned output arrays. Keep numerical optimization in the existing native libraries. | **Host + Addon.** Preparation currently captures and serializes Blender-owned geometry. Owning data can avoid some conversions and give workers safe access without Blender APIs. Sharing buffers requires explicit lifetime and memory ownership; zero-copy is not an assumed guarantee. |
| R02 Responsive preparation as well as solving | Keep input and navigation responsive during capture, initialization, solving, validation, and publication. Show acknowledgement before expensive work. Bound UI/render-thread work and avoid long document locks held by workers. | **Host + Addon.** Background solvers already exist, but preparation and publication can block. Blender's Python integration is not thread-safe; native work on owned arrays and separate processes already address part of that boundary. An application can design its ownership model around this requirement. |
| R03 One scheduler for interactive work | Coordinate required dependencies, previews, final solves, and advisory checks. Reserve interaction capacity, limit queues, merge obsolete pending edits, and batch invalidation and bookkeeping before dispatch. | **Addon.** Carry forward existing debounce, fiber priorities, and dirty-aspect scheduling. The improvement is coordination across subsystems and earlier batching; repeated overlap-refresh preparation was an observed example. |
| R04 Explicit edit transactions | Every drag and numeric edit has begin, update, commit, and cancel events. Update controls immediately, keep one understandable undo step, and reconcile asynchronous results with the transaction that requested them. | **Host + Addon.** Shortcut setters currently run synchronous work. Blender offers modal operators, but a specialized app can make gesture boundaries a common contract for every control instead of inferring them from multiple callback paths. |
| R05 Consistent update modes | Offer Live, On Release, and Manual behavior throughout the application, with explicit pending edits. Distinguish preview quality from final quality and preserve required dependency order. | **Addon + UX.** Subsystem controls already exist. The gain is consistent behavior across bone, fiber, muscle, and output editing. A timer's quiet period alone does not define when a gesture commits. |
| R06 Versioned results and cooperative cancellation | Associate jobs with document and dependency revisions. Reject stale results after further edits, undo, deletion, or loading. Acknowledge Cancel promptly and stop native work at safe checkpoints. | **Addon.** Fiber generation guards already exist. An October 15 source recheck also found `job_revision.attach` and `require_current` in the coordinated skin/topology path, superseding the October 12 missing-guard finding. Carry these protections forward and qualify their coverage. Long native operations still need cancellation checkpoints. |
| R07 Publication without a long final freeze | Prepare result buffers away from interaction, stage uploads within a measured budget, and switch to a complete valid result at a defined boundary. Reuse topology and buffers where possible; limit accumulated completed results. | **Host + Addon.** Writing Blender mesh/curve data is part of current publication. Direct renderer resource control creates opportunities to reduce that work, but synchronization, memory copies, and GPU upload stalls still need measurement. |
| R08 Stable output during computation | Keep the last accepted geometry visible, expose current controls, and mark pending or stale output clearly. Use approximate previews only where useful and visibly distinct from accepted geometry. | **Addon + UX.** Some retained-output and preview mechanisms already exist. Make them consistent; an approximate surface must not silently become collision truth or a validated downstream input. |
| R09 A useful activity panel | Show preparing, solving, validating, and publishing; elapsed time; affected entities; queued work; cancellation; and actionable failures. Let the user select an affected entity from a task entry. | **Addon + UX.** Progress and cancellation are distributed across tools. Counts need not imply time remaining. Distinguish a cancellation request from confirmed worker termination. |

Blender's restriction concerns access through its Python integration, not an assertion that its renderer or internal evaluators are single-threaded. The standalone advantage would come from safe data ownership and scheduling. [Blender threading guidance](https://docs.blender.org/api/5.0/info_gotchas_threading.html)

Explicit transactions also avoid treating Blender's message bus as a complete interaction stream: its documented notifications exclude viewport object movement, and callback changes are not included in the related undo step. [Blender message bus limitations](https://docs.blender.org/api/5.0/bpy.msgbus.html)

## Viewport clarity and selection

| Requirement | What I would prefer in the application | Connection to the work in this thread |
| --- | --- | --- |
| R10 Separate viewport state from authored data | Store hover, selection styling, opacity overrides, focus, and diagnostics in a presentation layer. Permit different presentations in different viewports. Hover changes render state without invalidating anatomy or entering document undo. | **Host + Addon.** Object-color writes affect Blender data shared by views. Our isolated alpha test emitted shading updates even for an identical assignment. Independent per-viewport styling needs a different drawing path in the addon; it can be a basic renderer feature in the application. |
| R11 Three opacity states | Provide default, hovered, and selected states, with selected taking precedence. Use role-specific opacity for muscles, fibers, and SCPs; preserve native SCP RGB colors. Keep thin fibers legible and supporting controls visible. | **Addon + UX.** Muscles already have inactive/active alpha, and fibers have active highlighting. Blender supports object alpha in Workbench. The gain is a consistent state policy with efficient updates, not the invention of transparency. |
| R12 A dedicated hover service | Coalesce movement, reuse picking data, query relevant candidates, and update styling only when the target changes. Handle curves and meshes explicitly. Refresh after view or geometry changes; bound first queries after edits. | **Addon + UX.** The inspected picker raycasts every candidate mesh, and its SCP path excludes curves. Compare cached native spatial indexing with renderer-assisted selection. GPU readback, cache invalidation, thin curves, and overlap remain costs; hardware picking is not an automatic win. |
| R13 Predictable selection through context geometry | Separate visibility from pickability. Provide category filters, a deliberate deeper-target action, and screen-space tolerance for fibers and handles. Hover must identify the same target that a click selects. | **Addon + UX.** A transparent muscle can intercept a ray intended for a visible fiber behind it. Transparency alone does not solve selection policy. Opacity changes must not change candidate eligibility and cause flicker. |
| R14 Anatomical entities as the editing unit | Select one muscle, fiber, or SCP and understand its surfaces, attachments, controls, and mirrored instances. Keep display instances and handles subordinate to stable anatomical identities. | **Addon + UX.** Source/mirror mapping already encodes much of this across Blender objects. A specialized model can expose anatomy directly and avoid making every drawn helper an independent document object. Rendering benefits need object-count and memory benchmarks. |
| R15 Independent presentation layers | Control anatomical surfaces, fibers, handles, attachments, and diagnostics independently. Keep context visible but optionally unpickable. Respect manual hiding when entering and leaving a temporary presentation. | **Addon + UX.** Category visibility currently groups anatomy with some helpers. Active-fiber handles are already limited to the active fiber; preserve that behavior and improve independence elsewhere. |
| R16 Task and region focus | Provide reversible views for shaping an SCP, editing a fiber, adjusting muscle volume, and reviewing the surface. Keep relevant supports and source/mirror relationships visible while fading unrelated content. | **UX.** Isolation, proxy view, and category controls are foundations. The preference is a coherent task-level interaction with predictable restoration, qualified against actual editing tasks. |
| R17 Readable depth and overlap | Combine transparency with optional silhouettes, local cutaways or clipping, and diagnostics on demand. Keep selected handles clear without drawing every helper through all surfaces. | **UX.** Exposing every underlying layer may worsen clutter and overdraw. Compare treatments at matching production views for fiber tracing, volume judgment, and control finding. The alpha capability test did not establish clutter reduction. |
| R18 Display detail independent of solve quality | Permit cheaper curve tessellation, helper drawing, and background display during navigation, restoring detail after interaction. Separate coarse display from geometry used for final attachments, collisions, and validation. | **Host + Addon + UX.** A dedicated renderer gives direct control over representation and batching. The audit did not establish rendering as the main bottleneck, so introduce these changes where viewport measurements justify them. |

Workbench already supports object-color alpha, and the October 12 Blender 5.0.1 probe verified it with global X-Ray disabled. The opportunity is control over the complete presentation and picking policy. [Blender viewport display documentation](https://docs.blender.org/manual/id/5.0/render/workbench/display_settings.html) and [probe evidence](evidence/viewport_opacity_2026-10-12.json).

## Reliability and development tools

| Requirement | What I would prefer in the application | Connection to the work in this thread |
| --- | --- | --- |
| R19 Explicit save and export presentation | Save authored data and intentional workspace preferences separately. Omit transient hover from canonical appearance. Preserve accepted geometry and identify stale caches. Provide a repeatable debug view for export and reopen checks. | **Host + Addon + UX.** Temporary visibility and alpha changes must not leak into deliverables. Blender exports must retain normal source/mirror fiber curves and native SCP colors through `StaticScene.save_debug_copy`. |
| R20 A document API independent of the active editor | Expose operations using explicit document and entity arguments, with structured results. Use the same operations from the UI, automation, and headless validation. | **Host + Addon.** Some Blender operators depend on area, mode, and selection context. Preserve AnthroForge's use-case and native layers; separate their remaining Blender adapters rather than replacing validated numerical work. |
| R21 Built-in interaction diagnostics | Measure input-to-feedback latency, actual frame times, hover time, queue delay, preparation, solving, publication, cancellation, and stale-result rejection. Record reproducible interaction sequences against identified fixtures. | **Addon.** Existing probes and telemetry are valuable. Setter timings and timer heartbeats do not establish smooth editing. Add real gesture replay and cold/warm production tests so responsiveness becomes a release criterion. |

Blender's operator documentation describes context-dependent invocation and status-style return values. An explicit document API would simplify automation, but it does not require rewriting functions that already avoid those operators. [Blender operator limitations](https://docs.blender.org/api/5.0/info_gotchas_operators.html)

## Implementation order and proof of benefit

1. **Establish the foundation:** R01–R07, R10, and R20. Separate authored state, evaluated geometry, and presentation state. Reuse native algorithms and make one complete edit transaction work with background execution, cancellation, undo, and revision-safe publication.
2. **Make that workflow comfortable:** R08–R09 and R11–R16. Demonstrate stable visible output, understandable pending work, three opacity states, and reliable fiber selection through context geometry.
3. **Expand where measurements justify it:** R17–R18. Compare cutaways, transparency treatments, display detail, and batching on actual production bottlenecks.
4. **Apply R19 and R21 throughout:** verify saved/reopened state and compare every stage against the same fixtures and gestures.

Initial acceptance targets remain input-response p95 below 50 ms and cancellation acknowledgement below 100 ms, with worker stop time recorded separately. Establish a declared reference machine, scene, and viewport size for a proposed 60 FPS navigation target; report frame-time percentiles and worst stalls. These are design targets, not standalone results.

The decisive comparison is an actual skull or body editing session: sustained dragging, typing, undo/redo, selecting a fiber behind a muscle, orbiting during a solve, cancelling, making a newer edit, and saving/reopening. Compare interaction latency, mistaken selections, time to useful preview, total completion time, and final geometry correctness. Measure static transparency separately from hover so overdraw costs are not mistaken for picking costs.

Existing C++ UI primitives such as Qt's promise-based concurrent execution provide progress and cooperative cancellation, while hardware-selection APIs such as VTK's demonstrate renderer-assisted picking. These are implementation references, not a toolkit selection: cancellation needs checkpoints, and visible-surface picking alone does not satisfy selection through transparent anatomy. [Qt concurrent execution](https://doc.qt.io/qt-6/qtconcurrentrun.html), [VTK hardware selection](https://vtk.org/doc/nightly/html/classvtkHardwareSelector.html).
